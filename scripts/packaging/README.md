# Release Packaging

This document covers packaging only. The root README is maintained separately.

## Automation

Pushes to `main`, including merged PRs, run Go 1.25 tests and vet on Linux,
macOS, and Windows before publishing. Pull requests also run the CI workflow.
Documentation-only and `bucket/` / `Formula/`-only changes are excluded.
The root package must be `main`, with a string variable `main.version` for
`-ldflags "-X main.version=..."`.

The release workflow starts with `v0.1.<github.run_number>` and increments the
numeric suffix if that tag already exists. Workflow reruns create a new unused
version rather than modifying an existing release. Releases point at the exact
triggering commit, not whatever `main` points at later.

The helper builds six standalone binaries with `CGO_ENABLED=0`:

- Linux amd64 and arm64: `.tar.gz`
- macOS amd64 and arm64: `.tar.gz`
- Windows amd64 and arm64: `.zip`

Archives contain only `cli-GPT-6.1-Sol-go` (or `cli-GPT-6.1-Sol-go.exe`) at the
archive root. Asset names are
`cli-GPT-6.1-Sol-go_v0.1.N_<goos>_<goarch>.<tar.gz|zip>`.
Each release includes `SHA256SUMS`. Generated package hashes cover the actual
release archives, not the uncompressed executables. No Go installation is
required by end users.

After publication, a fresh `main` checkout receives only the generated
`bucket/cli-GPT-6.1-Sol-go.json` and `Formula/cli-gpt-6.1-sol-go.rb` files.
Push retries fetch fresh `main` and reapply only those files; source changes are
never copied, reset, or force-pushed. An already-newer manifest is not downgraded.
Release runs are serialized, though GitHub concurrency may replace pending
runs when multiple pushes arrive quickly; this releases the surviving push,
not necessarily every intermediate commit.

The repository must permit GitHub Actions `contents: write` access and allow
the `github-actions[bot]` package-update commit on `main`. Branch protection or
rulesets requiring PRs may block this commit even with workflow write access;
configure a permitted automation identity/bypass if needed. A blocked update
fails the workflow but does not remove the already-published release.
Commits made with the default `GITHUB_TOKEN` do not trigger other push workflows,
which is desirable here. Path exclusions also prevent a package-only release
loop if an alternative token is used later.

Before the first successful release, the bucket and Formula folders contain
only placeholders. There are deliberately no fake URLs or checksums.

## Install After The First Release

### Scoop (Windows)

With Scoop already installed, run in PowerShell:

```powershell
scoop bucket add llm-supermarket https://github.com/llm-supermarket/cli-GPT-6.1-Sol-go
scoop install llm-supermarket/cli-GPT-6.1-Sol-go
cli-GPT-6.1-Sol-go --help
```

The manifest preserves the exact application name. Updates use
`scoop update cli-GPT-6.1-Sol-go`. Only 64-bit and ARM64 Windows are supported.
Manifests are regenerated by the release workflow, not Scoop autoupdate.

### Homebrew (macOS And Linux)

```sh
brew tap llm-supermarket/cli-gpt-6.1-sol-go https://github.com/llm-supermarket/cli-GPT-6.1-Sol-go
brew install llm-supermarket/cli-gpt-6.1-sol-go/cli-gpt-6.1-sol-go
cli-GPT-6.1-Sol-go --help
```

The explicit tap URL is necessary: the repository is not named
`homebrew-cli-gpt-6.1-sol-go`. Homebrew normalizes named formula lookups to
lowercase, so the practical formula filename/token is `cli-gpt-6.1-sol-go`,
with Ruby class `CliGpt61SolGo`. An uppercase filename would not resolve reliably
through ordinary named installs. The GitHub repository and installed binary
remain exactly `cli-GPT-6.1-Sol-go`.

Update with `brew update` followed by
`brew upgrade llm-supermarket/cli-gpt-6.1-sol-go/cli-gpt-6.1-sol-go`.
The formula chooses the published archive for the host OS and architecture.
These are standalone archives, not Homebrew bottles.

### Direct Download

Download the matching archive and `SHA256SUMS` from
<https://github.com/llm-supermarket/cli-GPT-6.1-Sol-go/releases/latest>.
Verify the archive's SHA256, extract it, and place the executable on your PATH.
Linux/macOS archives preserve executable permissions.

## Local Verification And Recovery

```sh
go test ./scripts/packaging
go vet ./scripts/packaging
go run ./scripts/packaging -version v0.1.42 -dist /tmp/cli-release -output /tmp/cli-packages
```

Use suitable absolute temporary paths on Windows. Do not commit local build
outputs. To regenerate manifests for an already-published release without
rebuilding (which could change hashes), download its six archives to a temporary
directory and run:

```sh
go run ./scripts/packaging -build=false -version v0.1.42 -dist /tmp/cli-release -output /tmp/cli-packages
```

Then apply only those generated manifests through the repository's permitted
commit/PR process. Recovery hashes the downloaded release assets exactly.
